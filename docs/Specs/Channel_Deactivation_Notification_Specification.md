# Спецификация: Уведомление пользователей о деактивации каналов

## Обзор

Спецификация описывает систему уведомлений пользователей Telegram при деактивации каналов, на которые они подписаны.

## Цель

Обеспечить своевременное информирование пользователей о деактивации каналов для улучшения пользовательского опыта и прозрачности платформы.

## Сценарии использования

### Основной сценарий
1. Администратор деактивирует канал
2. Система автоматически находит всех подписчиков канала
3. Каждому подписчику отправляется уведомление о деактивации
4. В логах системы отмечается успешная отправка уведомлений

### Альтернативные сценарии

**Сценарий 1: Канал уже неактивен**
- Система проверяет статус канала перед отправкой уведомлений
- Если канал уже неактивен, уведомления не отправляются

**Сценарий 2: Ошибка отправки уведомления**
- При ошибке отправки конкретному пользователю, система логирует ошибку
- Продолжает отправку остальным пользователям
- Создает задачу для повторной попытки

**Сценарий 3: Массовая деактивация**
- Позволяет деактивировать несколько каналов одновременно
- Каждому пользователю отправляется отдельное уведомление по каждому каналу

## Функциональные требования

### FR-1: Определение подписчиков
- Система должна уметь находить всех активных подписчиков канала
- Учитывать только активные подписки (не отписанные и не приостановленные)

### FR-2: Формирование уведомлений
- Уведомление должно содержать:
  - Название деактивированного канала
  - Причину деактивации (если указана)
  - Рекомендации по дальнейшим действиям
  - Возможность подписаться на другие каналы

### FR-3: Отправка уведомлений
- Уведомления отправляются через Telegram Bot API
- Используется фоновая обработка для отправки
- Поддерживается локализация уведомлений

### FR-4: Обработка ошибок
- Логирование всех ошибок отправки
- Механизм повторных попыток при неудачной отправке
- Уведомление администратора о критических ошибках

## Нефункциональные требования

### NFR-1: Производительность
- Отправка уведомлений не должна блокировать деактивацию канала
- Поддержка отправки до 1000 уведомлений в минуту

### NFR-2: Надежность
- Гарантированная доставка уведомлений или логирование неудачных попыток
- Резервный механизм отправки при сбоях

### NFR-3: Масштабируемость
- Система должна обрабатывать одновременную деактивацию до 100 каналов
- Поддержка до 10000 подписчиков на один канал

## Модель данных

### Subscription (подписка)
```ruby
class Subscription < ApplicationRecord
  belongs_to :user
  belongs_to :channel
  enum :status, { active: 0, inactive: 1, paused: 2 }
end
```

### Channel (канал)
```ruby
class Channel < ApplicationRecord
  has_many :subscriptions, dependent: :destroy
  enum :status, { active: 0, inactive: 1 }

  # Добавляем поле для причины деактивации
  attribute :deactivation_reason, :string
end
```

### NotificationLog (лог уведомлений)
```ruby
class NotificationLog < ApplicationRecord
  belongs_to :user
  belongs_to :channel
  attribute :notification_type, :string
  attribute :status, :string # sent, failed, pending
  attribute :error_message, :text
  attribute :sent_at, :datetime
end
```

## Правила валидации

### При деактивации канала
- Канал должен существовать
- Канал должен быть активен
- Администратор должен иметь права на деактивацию

### При отправке уведомлений
- Пользователь должен быть активен
- Подписка должна быть активной
- У пользователя должен быть подключен Telegram

## Ограничения и известные проблемы

- Отправка уведомлений зависит от доступности Telegram API
- Большие объемы рассылок могут требовать throttling
- Пользователи могут заблокировать бота после получения уведомления
